# 증강 윷놀이 — 1차 증강·이벤트 구현 검토 및 다음 작업 v5

기준: 2026-10-24 Claude Code 작업 결과 보고. 이 문서는 보고 내용을 기반으로 한 검토 지시서이며 실제 소스·테스트 실행 검증을 뜻하지 않는다.

## 1. 보고된 완료 항목

- `shared/src/effects.ts`: 패시브 4개(개 승급, 도깨비 장난, 모의 기운, 출발 대시), 액티브 3개(고정 투척, 위험한 도박, 두 번째 기회).
- 액티브 사용 조건·잔여 횟수 서버 검증, 카드 UI 상태(사용 가능/예약됨/사용 불가/소진), 효과 발동 알림·로그.
- 자동 이벤트 E5 왕의 몰락, E6 전원 출동 구현. 전원 4라운드마다 이벤트 우선 발동 후 해당 시점 증강 선택. 3.5초 동안 연출 및 입력 잠금.
- 탭별 비밀 토큰으로 새로고침 복귀. 대기실 30초 유예, 진행 중 게임 복귀 지원.
- 결과 화면에 선택 증강 표시와 2~3인 카드 중앙 정렬. 결과 화면은 아직 브라우저 완주 검증 미실시.
- 배포 및 최초 커밋은 아직 미실행.

## 2. 현재 보고 기준 우선 확인사항

### A. 자동 이벤트 E5 — 순위와 말 선택

1. '1위'가 단독 선두인지, 동점인 경우 누구에게 적용되는지 확인한다. 리롤용 점수(골인 말 수)와 E5 순위표 기준을 혼동하지 않는다.
2. 판에 말이 없는 선두 플레이어는 어떻게 처리하는지 정의한다(대상 없음 처리 등). 자동으로 임의 규칙을 결정하지 말고 확인 요청한다.
3. 업힌 말 중 한 개만 복귀시키는 현재 동작은 이벤트 예외 규칙임을 코드·테스트에 명시한다.
4. E5로 인한 복귀가 일반 '잡힘' 후속 효과·추가 던지기를 발생시키지 않는지 검증한다.

### B. 자동 이벤트 E6 — 동일 칸 공존

1. E6 출발은 잡기 없이 각 플레이어 대기 말 하나를 첫 칸에 배치한다는 현재 규칙을 유지한다.
2. 서로 다른 소유자의 말이 공존할 때 이후 이동·새로운 말 착지·잡기·업기 판정이 일관적인지 테스트한다.
3. 이 상태를 서버 데이터 모델이 안전하게 표현하고 클라이언트에서도 모두 선택·표시 가능한지 확인한다.

### C. 두 번째 기회 — 추가 던지기 처리

1. 윷/모 결과를 다시 던질 때 해당 결과로 예약된 미실행 추가 던지기가 정확히 취소되는지 확인한다.
2. 이미 추가 던지기가 실행되었을 때 되돌리기 허용 여부는 명세에 명확히 적고, 미확정이면 질문으로 남긴다.
3. 확률형 패시브(개 승급·도깨비 장난·모의 기운)의 발동 시점, 재추첨 여부, 연쇄 변환 방지 규칙을 테스트한다.
4. 출발 대시 이동 미리보기와 서버 실제 도착 경로가 일치하는지 검증한다.

### D. 리그레션·네트워크

1. 증강/이벤트 발동 중 18초 타이머, 20초 증강 선택 타이머, 재접속, 입력 잠금이 충돌하지 않는지 확인한다.
2. 다른 플레이어에게 자신의 증강 후보가 전송되지 않는지 소켓 payload를 확인한다.
3. 효과 미구현 증강 101개가 실제 선택에 나올 수 있다면, 테스트용 의도인지 명확히 표시하고 실플레이 활성화 정책을 결정한다.
4. 전체 테스트를 다시 실행하고 실패 항목 및 테스트 총합을 진행 현황에 기록한다.

## 3. 배포 전 완료할 통합 테스트

- 2인, 3인, 4인 각각 방 생성 → 입장 → 첫 증강 선택 → 윷 던지기 → 말 이동 → 잡기/업기 → 4라운드 E5 또는 E6 → 증강 선택 → 한 명 4말 골인 → 결과 화면.
- 타임아웃 자동 윷 던지기/이동/증강 선택.
- 증강 선택 중 새로고침, 자신의 차례 중 새로고침, 접속 끊김 2초 후 자동 진행과 재복귀.
- 효과 발동 로그와 결과 화면 '함께한 증강' 데이터 정합성.
- 각 테스트에서 클라이언트와 서버가 동일한 말 위치·턴·승패를 유지하는지 검증.

## 4. 작업 순서 요청

1. 이번 보고에 나온 규칙 A~C를 코드에서 확인하고, 변경이 필요한 **규칙 결정 사항**은 사용자에게 질문 목록으로 정리한다.
2. 기능별 테스트 및 전체 2~4인 완주 통합 테스트를 수행한다. 미완료면 완료라고 쓰지 않는다.
3. 문제가 드러난 로직만 최소 범위로 수정한다.
4. `progress.md`에 검증 내용/테스트 수/실패·보류 내용을 반영한다.
5. Figma 화면은 임의로 바꾸지 않는다. UI 변경이 필요하면 별도의 **Figma AI 요청 사항** 목록으로 정리하고, 사용자 승인 전 디자인을 수정하지 않는다.
6. 최초 커밋, GitHub 푸시, Render 생성, 실제 배포는 아직 수행하지 않는다. 사용자가 명시적으로 요청하면 그때 진행한다.
